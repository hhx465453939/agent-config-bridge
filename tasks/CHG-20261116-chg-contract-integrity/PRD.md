# PRD：CHG 契约门控升级为「契约成立」

- change_id: CHG-20261116-chg-contract-integrity
- 产品面：开发者体验 / 交付质量

---

## 1. 用户与场景

| 用户 | 场景 | 现在的痛 |
|---|---|---|
| 在 pi 里做开发的本人 | 让 agent 开发一个新特性 | agent 写一个 SPEC.md 就开工，PRD / TRACEABILITY 根本不存在，回头没法验收 |
| 同上 | 同时开着多个仓库 | 读 A 仓库的老 CHG，就能解锁在 B 仓库改代码 |
| 同上 | 隔了几个月的新需求 | 读 `CHG-001` 的 SPEC 也算「核对立项」，实际跟今天要做的事毫无关系 |
| 同上 | 写完代码想复核 | SPEC 没写验收判据，只能凭感觉判断「做完了」 |

## 2. 需求条目

| # | 需求 | 优先级 |
|---|---|---|
| R-1 | 改代码前，本项目必须存在一份**齐全**（SPEC + PRD + TRACEABILITY）的 CHG 契约，且本会话读过它 | P0 |
| R-2 | SPEC 必须写清验收判据，否则视为「没法定终态」 | P0 |
| R-3 | SPEC 的 `status` 若声明为草稿态，不予开工 | P0 |
| R-4 | 契约必须落在本次要改的仓库内，跨仓库不算 | P1 |
| R-5 | 拒绝信息必须能直接指导下一步：缺哪一件、缺什么段、status 是什么 | P0 |
| R-6 | 不用 CHG 体系的仓库（以 ADR 管理）不受影响 | P1 |
| R-7 | 既有 11 个 CHG 不得被新判据误杀 | P0 |

## 3. 承诺什么

- 承诺：**只写一个 SPEC.md 就开始改代码**这条路径会被拦住，且拦的时候告诉你要补哪两件。
- 承诺：拒绝文案逐条列出缺口，不是一句「未核对立项」。
- 承诺：跨仓库、跨历史 CHG 的「假解锁」被关掉。
- 承诺：配置清空时可退回旧语义，便于排查误杀。

## 4. 不承诺什么

- 不承诺校验「目标文件在该 CHG 的独占清单里」——清单是自然语言，解析不可靠。
- 不承诺校验 CHG 状态机的流转正确性（approved 之后是否真的进入 executing 由流程保证，不由门控保证）。
- 不承诺阻止「补一个空 PRD.md 凑数」——门控只能校验存在性与关键词，不能校验思想质量。
  真正的内容质量靠 `TRACEABILITY.md` 与人工复核，不靠正则。

## 5. 判定口径说明（给使用者）

| 场景 | 结果 |
|---|---|
| 没 `tasks/` 目录 | 不拦（该仓库不采纳 CHG） |
| 有 `tasks/` 但无 `CHG-*` | 不拦（ADR 体系仓库） |
| 有 `CHG-*`，本会话没读任何契约 | 拦 `CHG_CONTRACT` |
| 读的契约在别的仓库 | 拦 `CHG_CONTRACT`（不算数） |
| 读了本项目契约，但缺 PRD.md | 拦 `CHG_CONTRACT_INCOMPLETE`，点名缺 PRD.md |
| 读了本项目契约，齐全，但 SPEC 无验收段 | 拦 `CHG_CONTRACT_INCOMPLETE`，点名缺验收判据 |
| 读了本项目契约，齐全，`status: draft` | 拦 `CHG_CONTRACT_INCOMPLETE`，点名 status |
| 齐全 + 有验收 + `status: approved` | 放行 |
