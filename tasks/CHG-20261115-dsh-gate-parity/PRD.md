# PRD：DSH 端门控对齐

- change_id: CHG-20261115-dsh-gate-parity
- 产品面：开发者体验 / 交付质量

---

## 1. 用户与场景

| 用户 | 场景 | 现在的痛 |
|---|---|---|
| 在 DSH 里做开发的本人 | 让 agent 改一个项目 | agent 直读源码、不查图谱，规则文档写了也没用 |
| 同上 | agent 回复「我稍后再补」就收工 | dsh 端没有任何轮次级拦截，承诺被当成交付 |
| 同上 | agent 用一条空查询换全仓库读权限 | dsh 端图谱信号在准入时就记，查没查、查没查到都不管 |
| 同上 | agent 调 `cat` / `Get-Content` 绕开 `read` | 部分覆盖（v5 已拦），但读成功后不留证据，后续判断失真 |

## 2. 需求条目

| # | 需求 | 优先级 |
|---|---|---|
| R-1 | 图谱信号必须来自**有内容**的查询结果，空结果不算 | P0 |
| R-2 | 轮次收尾扫描最终文本，第一人称拖延承诺要强制续跑 | P0 |
| R-3 | 读证据（inspection / convention / CHG 契约）来自真实成功的结果 | P1 |
| R-4 | 同一失败命令原样重试第 3 次要拦 | P1 |
| R-5 | 每轮注入提醒与域分类，分类输入含用户提示词 | P1 |
| R-6 | 破坏性 confirm 档在审批通道可用时走审批，不可用时维持既有放行 | P2 |
| R-7 | AI4S 产出物（Worklog / 结果 README）缺失时，轮次收尾要续跑 | P2 |
| R-8 | 文档与技能不再宣称「dsh 不支持结果钩子与轮次级注入」 | P1 |

## 3. 非目标

- 不让 dsh 端比 pi 端更严格（两端判定一律走 `policy.js` 同一份逻辑）
- 不新增用户可见的配置项；新行为一律复用既有 `policy.config` 字段
- 不追求「零误伤」——误伤有 `max_blocks_per_session` 与 `slack_max_continues` 两道上限兜底

## 4. 验收口径

用户视角的一句话：**在 dsh 里故意违规（直读源码 / 空查询换权限 / 只许诺不动手），会被拦或被迫续跑**；
守规矩时**感觉不到**这道门控（只多一次 Map 查找与一次正则）。

## 5. 风险接受

- `tools/result` 若在某次升级后改名，图谱证据会退化为「永不满足」→ 所有源码读被拦。
  接受理由：这是**显式**的失败（用户立刻看到拦截文案），比静默放行好；且
  `signal_ttl_ms` 到期后仅影响新窗口，不会让已打开的文件失效。
  缓解：加载时探测 `ctx.on` 是否接受 `tools/result`，失败则写 stderr 一行降级告警。
