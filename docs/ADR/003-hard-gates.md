# ADR-003 — 把规则文档变成硬闸门（gate），并抽取为可移植的策略层

```yaml
adr: 003
change_id: CHG-001
status: proposed
date: 2026-09-27
deciders: [user]
```

## 背景

`AGENTS.md` / `CLAUDE.md` 这类规则文档是**建议**：模型读了、通常照做。但有一条规则不是建议 —— "读源码之前先查代码图谱"。这条规则的收益只有在**真的执行**时才成立，而模型偶尔会跳过它。

Claude Code 的产品结构比较精致，能用 hooks 这类一等公民机制兜住；pi、DeepSeek Harness 这类较新的 harness 没有那么多内建的"结构"，所以**用扩展/插件把规则文档里最关键的那几条落成硬门控**，价值反而更高。

本机已经有一份跑了一段时间的参考实现（pi 扩展 `graph-first-gate.ts`），用户要求把它**抽象出来、放进本项目、并按 agent 铺开**，优先 pi 与 DeepSeek Harness。

## 决策

### 1. 策略层与适配层分离

规则逻辑（"什么算代码文件"、"哪些查询算数"、"拦截几次后放弃"）写在 `bridge/gates/policy.js`，纯 JavaScript，**完全不知道自己在哪个 harness 里跑**。

```
bridge/gates/
  policy.js          纯逻辑：作用域判定 + 检查项 + 会话状态 + 提醒文案
  pi/                pi 适配层（薄）
    index.js         pi.on('tool_call') -> policy -> { block, reason }
    policy.json      pi 的默认策略
  dsh/               dsh 适配层（薄）
    index.js         ctx.on('tools/pre-execute') -> policy -> { kind:'deny' }
    policy.json      dsh 的默认策略
```

两个 harness 的判定语义其实一样，只是词汇不同：

| | pi | dsh |
|---|---|---|
| 拦截点 | `pi.on('tool_call')` | `ctx.on('tools/pre-execute')` |
| 拒绝 | `{ block: true, reason }` | `{ kind: 'deny', reason }` |
| 查询成功的信号 | `pi.on('tool_result')`，`isError === false` | 见下方差异 2 |
| 逐轮提醒 | `pi.on('context')` 改写最后一条 user 消息 | 本项目未注入 |

### 2. 与参考实现的三处刻意差异（都写进注释，不藏）

1. **项目作用域自动探测**，不再硬编码"我的项目在 `/home/<某人>/Development`"。
   参考实现把作者的家目录路径写成常量；那在一个要给别人用的工具里是错的。现在按"配置了 `project_roots` 就用配置，没配置就沿目录向上找 `.git`"处理。
2. **dsh 的信号记录在查询被放行时，而不是返回成功后**。
   dsh 的结果结构比 pi 复杂，如果对它的成功判定写错，闸门会**静默失效**（永不打开）。错在"早一点打开"比错在"永不打开"安全，所以选了前者。这是可接受的，因为闸门防的是"根本不查"，不是"查了但查询本身失败"。
3. **dsh 不注入逐轮提醒**。
   dsh 的等价能力（向提示词贡献文本）属于它自己的插件体系，本项目不擅自模拟。拦截理由本身已经带了补救指引。

### 3. 闸门走正常受管路径，因此天然可撤回

安装闸门 = 往扩展目录写若干文件（`policy.js` / 适配器 / 生成的 `policy.json` / `README.md`），**走和其它受管内容完全一样的计划动作**。结果是：

* `adopt` 时它们被快照 → `revoke` 能把扩展目录恢复到 adopt 前的样子；
* 用户自己的扩展（在同一父目录里的其它文件）不受影响；
* `diff` / `doctor` 对闸门文件的漂移报得和普通文件一样。

**唯一的一处清单例外**：`never_touch` 里声明 `.pi/agent/extensions`（承诺不碰用户自己的扩展），闸门又要装在它里面。解决办法是**只豁免清单自己点名的那个子目录**（`<extension_dir>/<install_as>`），而不是整目录豁免；`doctor` 会报告这条例外。

### 4. 装进去 ≠ 生效：`auto_load` 必须如实声明

* pi 会自动加载扩展目录，所以 `auto_load: true` 名副其实。
* **dsh 不会自动加载扩展目录** —— 插件必须被 Cordis 组合显式挂载。所以 dsh 清单里 `auto_load: false`，`status` 与生成的 `README.md` 都会明确写出"已安装但尚未挂载，需要你自己加一行 plugin row"。

这个区分很重要：装到 dsh 里却不挂载，会让人以为"我在用了"，其实一条规则都没执行。宁可显得麻烦，也不能给假安全感。

### 5. 失败方向：策略文件读不出来就**放行**（fail open）

策略文件缺失或 JSON 坏了 → 闸门不生效，并明确告警。

理由：闸门坏了就把 agent 彻底卡死，比"某条规则暂时没执行"严重得多。反过来，"写入包含真实凭据的内容"这类规则**必须**失败关闭 —— 所以它们是独立的检查项（`no-secret-write` / `no-write-outside`），而不是依赖"策略加载失败"这个状态。

### 6. 每个会话最多拦截 N 次（默认 3）

防线之外的最后一道保险。参考实现已有这个设计，抽出来时保留：一条写错的规则最多浪费 3 次往返，之后放行，坏不了事。

## 被否方案

### 方案 A：每个 harness 各写一份完整实现

* 优点：各自最贴合、不需要抽象。
* 否决原因：**规则逻辑会分叉**。哪天改了"哪些扩展名算代码"，就得记住改三处，漏一处就出现"pi 管、dsh 不管"的静默不一致。
* 处置：策略层唯一，适配层薄。适配层薄到可以一次读完 —— 这对"审计闸门到底拦了没有"很重要。

### 方案 B：用 Bash Hook 之类的通用机制统一

* 否决原因：pi 的 hooks 与 dsh 的 Cordis 插件是两套完全不同的东西，硬凑一个"通用 hook"最后会变成两套 if 分支拼在一起，比分开写更难懂。
* 处置：接受"每个适配层独立"，但把公共部分压到只剩策略层。

### 方案 C：把闸门做成 npm 包，让各 harness 通过包管理器安装

* 优点：更"正规"，有版本号。
* 否决原因：用户的核心诉求是"**把本机的落实过程抽出来放到这个仓库里，让 agent 用它**"，而不是发一个包。走包管理器还会引入构建步骤、发布流程和版本漂移，与"零第三方依赖、可通读"的目标冲突。
* 处置：仓库内直接是可用产物；将来真需要发布再包一层，不影响现在。

## 后果

### 正向

* 规则文档里最关键的一两条**真的会被执行**，而且执行逻辑与 harness 解耦；
* 装上、升级、撤回都走已有的受管路径，不需要给闸门单独做一套生命周期管理；
* 离线可测：策略层有纯逻辑单测（`bridge/test/gates.test.js` 58 项），适配层用假 harness 对象驱动，不需要真的启动 pi 或 dsh。

### 负向 / 需接受

* 新增了一份"代码型受管资产"，比复制文件复杂一点（因此有专门的 `bridge/lib/gates.js` 与独立的测试组）；
* `never_touch` 的豁免是一条需要理解的细则（ADR 里写清、`doctor` 报告）；
* dsh 的挂载需要用户手动加一行 —— 这是 dsh 的设计决定的，不是本项目的偷懒；
* Kimi Code 没有任何用户可装的扩展机制，**它拿不到闸门**。这一点在 `status` 里明说，不装作已覆盖。
